# cs：本项目维护入口

先读根 `AGENTS.md` 与 `.codestable/attention.md`，按范围读取 lessons、specs 和相关 change。项目分工以 `ADR/reference/workflow-integration.md` 为准。

## 路由

| 诉求 | 动作 |
|---|---|
| 新功能、改变产品行为、大需求 | 已有明确 change 且要求实施时转 `openspec-apply-change`；提出明确新变更转 `openspec-propose`；探索范围转 `openspec-explore` |
| Bug、异常、性能回退 | `cs-issue`；只要求诊断时不修代码 |
| 行为等价重构、主动等价优化 | `cs-refactor` |
| 只读审查代码、方案或文档 | `cs-review` |
| 记住教训、更新知识指针 | `cs-keep` |
| 最小知识骨架接入 | `cs-onboard` |
| README、教程、既有设计说明的整理维护 | 在当前会话按下述文档流程处理，不发明不存在的文档 skill |
| 询问怎么做、该用哪个 | 只解释或推荐，不执行 |

## 执行边界

- 明确授权后在同轮进入对应流程，但转交不扩大授权；提出方案不等于获准实施，不自动从 propose 跳到 apply。
- Bug 以相关契约、测试、可核实历史行为及用户明确期望为证据。规格缺失且期望不清时先澄清，不能擅自改需求。需要新增或改变预期行为时交给 OpenSpec。
- 重构中夹带的新行为拆出并交给 OpenSpec，不在维护任务中顺手实现。
- 不创建 CodeStable 功能包、产品 Epic 或第二套需求/验收/tasks。work 只在跨会话需要时记录恢复位置和证据指针。
- 目标技能不可用时报告缺失入口，不假装已调用，不退回已移除的功能工作流。

## 文档维护流程

1. 确定目标文档及唯一事实归属，读取正文、相关源码或验证证据。
2. 区分表述整理与行为变更：后者交给 OpenSpec；来源冲突先核实，未决产品含义交给用户。
3. 在原有归属内编辑，其他位置保留链接；不在 README、ADR 或 lessons 复制产品契约。
4. 检查链接、命令、术语与事实一致性；报告实际改动及验证，未执行的命令不得写成已通过。

仅咨询不写文件；用户只要求讨论时不开始实现。grilling 的已确认选择可交给 OpenSpec，建议或沉默不算批准。
