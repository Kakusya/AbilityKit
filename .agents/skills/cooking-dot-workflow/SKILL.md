# Cooking dot workflow

Use only on explicit invocation. The invoking main conversation is the sole coordinator; dot owns technical planning and final technical decisions, and Orca supervised worktree workers implement. This skill is instructions, not a background service: no main session means no automatic continuation. Installation is not a pilot or authorization to activate any Cooking task.

## Authority and entry

1. Read [AGENTS](../../../AGENTS.md), [Cooking progress](../../../Docs/design/CookingGame/progress.md), [Cooking index](../../../.trellis/spec/cooking/index.md) and [delivery SOP](../../../.trellis/spec/abilitykit/supervised-issue-delivery.md). Preserve Cooking-only scope, deferred/unapproved Unity, fixed ET versions and truthful evidence rules. Shared changes require a named approved Cooking consumer, necessity and acceptance per file. Existing `orca-ready` tags and old #6 approvals unlock nothing; `issue6-test-gate-results` stays stopped and isolated.
2. Load the available `orca-cli` skill, resolve its executable once by its discovery rules, and fetch that executable's live `skills get orca-cli --json` and `skills get orchestration --json` guides. Read only their references needed by the next action. Discover current capabilities and identities; do not embed machine paths, handles, repository IDs, browser refs or a default dot ID. Missing/unsupported capabilities stop the dependent action; do not invent commands or install global tools.
3. Before creating a new flow, read [recovery](references/recovery.md) and enumerate existing skill workflows across Git/Orca worktrees and Trellis tasks. Resume a unique unfinished flow automatically only after authority reconciliation; multiple candidates require Owner selection. An unrelated `in_progress` task is not a skill workflow. An active old coordinator or unknown Run authority prevents takeover.
4. For a new flow, align the requirement and observable acceptance in its owning Trellis task. Obtain Owner approval once for requirements and scope; then delegate technical planning without repeatedly seeking the same approval. Record the explicit invocation and approval provenance (session/message/date and exact scope), repository, task branch and target integration branch. Invocation with an approved requirement authorizes dot dialogue and task-scoped branch pushes, Issue/PR writes, and conditional automatic merge/close below. Reading/installing the skill alone authorizes none of these; publication and resource deletion always require separate authorization.

Trellis owns plans, status, research and evidence; use existing task lifecycle and manifests, not a second status system or changed task schema. GitHub Issues hold short current contracts and task links; PRs hold diffs. Orca owns actual Run/Dispatch/process facts. Keep durable intent/receipt records in the owning task as specified in recovery before any external effect.

## Plan and implement

- Confirm actual Git remote owner/repository against Orca metadata before remote writes; stale project metadata is not a destination. Explicitly target the verified repository. Read each Issue's latest body, labels, dependencies and approved scope before acting.
- Push a scoped task-branch commit containing requirements, relevant source and evidence that dot can read. Read [dot dialogue](references/dot-dialogue.md) before communicating. Dot can only converse and read GitHub commits: never invoke cloud work, code execution or GitHub writes through dot.
- Present complete technical conflicts, alternatives and raw evidence to dot; implement its explicit final technical decision. Owner scope and truthful evidence prevail: an out-of-scope decision stops that part and goes back with the conflict, rather than silently expanding scope or falsifying results. Preserve historical decisions. Record dot's plan and request/response identities in Trellis PRD/design/implement/manifests; review these artifacts before entering implementation.
- Use one Orca Run coordinator and only Orca managed-worktree workers, normally one, at most two with independent file, contract and resource owners. Ordinary/native subagents cannot replace these workers. Each dispatch names exact files, Cooking consumers, invariants, acceptance, current bounded assignment and stop boundary; workers are not alone and must preserve others' edits. Use configured Orca model/effort defaults and record actual effective values; unknown values remain unknown. Serialize exclusive .NET checks across workers/worktrees.
- Require proof of accepted input and actual turn start. Workers follow their live preamble for questions, heartbeats, inbox checkpoints and exactly-once `worker_done` with both Task and Dispatch IDs and explicit outcome. A send receipt is not a result; stale completions cannot settle a newer attempt. Reconcile ambiguous launches before any retry.
- During every dot wait, stop new dispatch, technical decisions and integration/merge. Existing workers may finish only their current bounded assignment and idle; a worker needing a new decision waits. Owner scope withdrawal overrides permission to finish: stop affected work immediately through supported authority, preserve evidence and prevent subsequent dispatch.

## Accept and deliver

1. Independently inspect final diff, per-file scope/consumers and raw results. Record source SHA/dirty, tool versions, commands/exits, declared and actual coverage, logs and binary identity where applicable. Use Passed / Failed / Blocked / Skipped / NotRun; non-applicable checks are N/A. Required missing environments, zero declared test execution, stale artifacts and SHA mismatch cannot pass. Verify real CI/required checks, not configuration references.
2. Give dot the exact final candidate commit and complete findings for explicit final acceptance of that request and SHA. Any new code invalidates old acceptance. Dot acceptance and coordinator scope/evidence checks are both necessary; a required NotRun or Failed check blocks delivery even if dot accepts.
3. With recorded task authorization, recheck current PR head, target branch, acceptance and actual required checks immediately before merge. Changes to the candidate or integration base require renewed affected checks and dot review of the resulting candidate as needed; never apply old acceptance to changed code. Checkpoint the intent, merge only the approved candidate, then record actual merge identity. Reconcile lost receipts before retrying.
4. Run required integration checks on the actual merged source, preserving its source/binary identities. Only successful required integration permits automatic Issue close and task archive. A postmerge failure retains the failure and open completion exits; repair under the same bounded technical review process or use an explicitly reviewed rollback. Do not mark complete or close to conceal failure.
5. End when this requirement is delivered. Record other discoveries as candidate backlog only. Account for every settled terminal: reuse only for approved current work, retain under explicit Owner permission, or release only with separately authorized cleanup. Dot timeout/failure uses the resource-safe pause and retention contract in the references; never blanket close/delete.

Disk presence does not prove the host loaded the skill. If it is unavailable in the host catalog, explain the refresh/new-session requirement before a live pilot; do not claim live validation from static document checks.
