# ADR-0002：权威固定 Tick 与首阶段状态同步

- 状态：Accepted（用户已明确技术路线；不代表功能已实现或已测试）
- 日期：2026-09-14
- 来源：用户确认的做菜经营游戏技术路线

## 上下文

做菜经营游戏需要在主机玩家和局域网客户端之间共享可裁决的交互，同时保持 AbilityKit 框架与应用层边界。现有框架分别提供逻辑 World、Host、FrameSync、StateSync、Snapshot、Record 等机制，但不因此替应用决定烹饪领域模型、listen session、wire codec 或业务状态导出。近期目标是局域网合作，公网连接后置；玩家主机角色见 [ADR-0001](0001-player-host.md)。

严格 lockstep 能降低状态带宽，但要求随机、排序、数值、碰撞、恢复和缺输入等全链路确定性；现有 `FramePacket` 携带输入或快照的能力不等于跨机器严格 lockstep。

## 决策

1. 游戏模拟采用权威固定 Tick 的纯 C# 路线；网络线程只入队，模拟线程按稳定顺序验证并提交命令。
2. listen host 的本地玩家与远端玩家使用同一套命令验证路径。拾取、放下等交互必须是验证后原子提交，并处理生命周期、资格、范围、容量、可用性、位置、幂等和同时争抢仲裁。
3. 首阶段以权威状态同步和快照作为同步基线，而不是严格确定性 lockstep。客户端按快照版本/顺序处理，表现插值和局部预测仅是测量后可启用的优化。
4. 30Hz 只作为原型候选值，必须由响应性、负载、网络和玩法测量决定，不是锁定要求。
5. 逻辑 Tick 独立于渲染帧；烹饪计时依赖模拟 Tick/逻辑时钟，不依赖动画回调或墙钟。

本决策不定义具体配置表、配方、人数、平台、存档归属、房主退出、断线恢复或主机迁移语义；这些属于应用需求，须在对应 Trellis task 的 PRD、design、implement 和检查证据中形成可审阅的边界。

## 替代方案

- **严格 lockstep**：保留为后续测量和验证后的可能路线；当前不采用，因为跨机器全链路确定性前提尚未建立。
- **直接依赖 Rigidbody/渲染帧**：不采用；跨机器物理与渲染频率不能作为模拟确定性基础。
- **客户端直接写权威状态**：不采用；会破坏同一路径验证、所有权和原子性。

## 影响

- 首阶段需建设烹饪领域状态、LAN listen session、wire codec 和业务快照/状态导出，不能把框架现有机制当作完整游戏实现。
- 固定 Tick 与稳定仲裁便于测试、回放和后续测量；状态同步需要处理版本、乱序/旧快照、基线快照和可选预测校正。
- 若以后转向严格确定性，必须补齐随机种子、排序、数值/碰撞、状态恢复与 hash、缺失输入、预测 rollback 等证据，不能仅凭 `FramePacket` 宣称完成。
