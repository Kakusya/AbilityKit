## Crucial failure distinction

Every successful retry control declares BeginEnd(Failed) explicitly while the Host is healthy. No normal unmet order or low score causes Failed; natural zero-star service success is separately verified. Actual command/tick exceptions are covered by CookingLevelEtHostTests.Fixed_tick_failure_is_rethrown_faults_host_and_does_not_publish_frame_sequence, Throwing_wash_port_terminalizes_failing_and_remaining_admitted_envelopes_once and Fixed_step_failure_after_accepted_command_preserves_the_command_effect_and_final_history. These paths latch _tickFailure, and Host.Check refuses further ordinary lifecycle/generation operations. BestEffortAbortLifecycle concerns installation/binding cleanup and uses Aborted, not Failed. Therefore existing evidence does NOT demonstrate a runtime exception automatically transitions to Failed or allows same-faulted-Host CreateRetry.

Recommended precise contract: technical-Failed is an explicit application/owner outcome on a healthy lifecycle; a faulted runtime must be disposed and the last durable confirmed baseline loaded into a fresh Host. Do not add a new business failure rule or silently clear the fault latch. If automatic fault-to-Failed same-Host retry is actually desired, it needs explicit design beyond current evidence. Coordinator has been notified of this distinction.

CreateRetry receives caller-provided in-process progress and ApplyRetryChoices; independently reconstructed confirmed-choice validation currently belongs to durable save/load. A locked caller object alone is not evidence of persisted trusted choices. A consolidated test should use the actual Progress returned by trusted LoadMajorBaseline (or explicitly trusted application input), not rehashed saved self-grants.
