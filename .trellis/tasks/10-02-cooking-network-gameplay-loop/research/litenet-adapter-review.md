## Receive data lifetime, threading and polling

Local official NuGet `LiteNetLib/2.1.4/lib/netstandard2.1/LiteNetLib.xml:2815-2822` explicitly documents GetRemainingBytes as allocating a new byte array and advancing the reader. The old adapter calls it before returning from NetworkReceiveEvent (`:54-58`), with AutoRecycle=true (`:61`). The ArraySegment passed upward therefore does not refer to the packet-reader pooled buffer. Retaining it in a queued dispatcher is safe at this copy boundary. Replacing it with GetRemainingBytesSegment/Span/Memory without an owned copy would change that guarantee.

The same XML at `:718-726` says UnsyncedEvents runs callbacks on another thread without PollEvents; UnsyncedReceiveEvent uses the receive thread. Consequently the adapter needs no new Poll API and Cooking must not drive NetManager polling from its logical Tick. Background callbacks may decode/copy/enqueue, never mutate ET gameplay. ServerNetworkSession defaults both dispatchers to Inline (`:41-42`), so packet callbacks are not automatically moved onto an application owner thread. For a queued IO dispatcher, it already copies input before posting (`:138-149`). A dispatcher used with its stateful frame decoder must preserve per-session order and serialize decode; a generic thread-pool dispatcher must not be presumed to do so.

No callback-order or callback-thread serialization guarantee was established by the reviewed interface/XML. Admission-vs-first-receive and disconnect-vs-queued-decode need explicit tests. In particular, old OnConnected puts a channel in the peer map before the external subscriber installs receive handlers. If receives can interleave during that handoff, OnBytes can see no subscriber and drop the application frame. This is a risk to verify, not a reproduced product failure. A retained pre-transfer buffer, or a proved serialized handoff contract, is needed if that test exposes it.

## Required corrections and unresolved lifecycle risks

1. **Transferred channel ownership:** old listener Dispose (`:86-99`) closes every mapped channel and stops their shared manager, including channels already handed to a subscriber. The interface says ownership transfers; the Dispose allowance specifically concerns channels never transferred. NetworkHost's usual Dispose closes sessions before disposing the listener, but that usage pattern does not make standalone listener disposal comply. Track handoff ownership and shared-manager lifetime, or explicitly settle the existing contract before implementation. Do not silently change framework semantics. Admission Stop should leave transferred peers usable; final manager shutdown should happen after the relevant channel owners release their leases.
2. **Exception-safe closure:** old channel OnBytes/Send catch clauses (`:119`, `:127`) invoke Error before Close. If an Error subscriber throws, cleanup is skipped. Closed can also throw from OnClosed (`:121`). Listener admission failure invokes Error after disposal (`:82`), potentially escaping a background callback. Ensure cleanup runs in finally and a subscriber exception cannot prevent cleanup of other channels or manager.Stop. Dispose's loop needs the same protection.
3. **Close races:** Close (`:129`) checks Volatile then calls peer.Disconnect before Interlocked marks closed. Concurrent Close/Dispose/network disconnect can issue multiple disconnect attempts or invoke callbacks after a lifecycle boundary. Atomic terminal state must protect physical close and exactly-once notification; do not call user callbacks under the listener lock. Verify Send against concurrent Close and Dispose, not just sequential idempotence.
4. **Failed bind/start cleanup:** the temporary manager in Start (`:61-62`) is not assigned until bind succeeds. A false/throwing Start needs explicit cleanup and a reusable listener state. Start after disposal, duplicate Start, Stop/start on the retained manager and a real occupied-port failure need tests. Endpoint's last value is not an active-listening assertion; IsListening is the admission state.
5. **Peer mapping:** use NetPeer object identity as a connection lifetime key; do not reuse remote endpoint text as identity. Map removal currently depends on PeerDisconnected (`:48-52`), so accepted-channel Close must eventually detach even if shutdown prevents that callback. Listener IDs are instance-local; application connection generation/Participant binding and rejection of old callbacks remain N01 Session responsibilities. IPv6-only bind and RemoteEndpoint formatting should be explicit rather than inferred from `_address + ':' + port`.
6. **Existing client transport:** master LiteNetTransport has the same safe GetRemainingBytes copy (`:60-65`) but does not explicitly enable AutoRecycle or recycle the reader, ignores the bool from manager.Start (`:69-71`), does not subscribe NetworkError, and does not clear peer state on PeerDisconnected (`:59`). Treat these as cleanup/error-reporting risks to verify/fix with the adapter, not grounds to replace ITransport. Dispose currently calls Close; decide whether reconnect-after-Close is allowed and enforce terminal Dispose separately if required. Do not claim an observed packet-pool leak merely from the missing explicit option without verifying the library default/runtime behavior.
7. **Cancellation boundaries:** neither generic channel interface has a cancellation-token API. NetworkHost already cancels queued/active requests on session close and supports StopAsync drain/cancellation (`NetworkHost.cs:150`, `:228`, `:379`, `:540`). Reuse this. It does not cancel Cooking's separate accepted ingress by itself; current N01 assigns that to owner-handled Connection events and generation revocation. A queued callback after Dispose must not republish an old session or advance gameplay.
