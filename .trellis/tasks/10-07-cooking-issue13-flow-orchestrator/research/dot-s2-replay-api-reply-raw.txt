三、网络重放的必要条件

本次 compete/replay 仍然先取得胜者的正式 Accepted 结果，再发起重放。

通过 C13-IDEMP 必须同时满足：

当前绑定相同。
同 run/attempt/generation、同 role/actor、同完整 scope、同 server instance；重放前后该 client 自己的 connection generation 不变。使用真实 Join/已安装 baseline 和当前角色状态校验，不要求两个不同 client 的 generation 数字相等。

重放的是原命令。
新 CallId，原 BusinessId，完整 FrozenCommand 不变，包括 ExpectedItemVersion、Command 字段和 network SimulationBatch=0。不能根据最新 snapshot 重建命令，不能把领域映射后的 ID/batch 写回 wire FrozenCommand。

身份来自实际响应。
原调用及重放的实际 DomainCommandId 均非空、相同，实际 stable ID 与请求的 BusinessId 相符。
可以用现有 CookingNetworkWireCodec.DomainId(实际 server instance, 实际 scope, participant, stableId) 校验预期值，但计算值只能用于比较，不能填补缺失的实际 DomainCommandId。DomainId 的计算不含 connection generation；因此相同 DomainCommandId 也不能替代当前连接 generation 校验。

取得正式业务终态。
Completion=Terminal，BusinessResult 存在，无本次调用错误，且原生状态属于所验证的正式路径。

Offline：保留现有 NativeDisposition=Duplicate 的重放要求。
Network：允许 NativeDisposition=Duplicate；也允许已完成原调用为 Executed、本次缓存返回仍为 Executed 的路径。
两种网络路径都必须有 IsDuplicate=true 和下面全部内容约束。不能只凭这两个字段通过。
Conflicted、Cancelled、协议拒绝、未知/缺失状态不属于成功重放；缓存了某个拒绝或取消记录也不自动使它合格。

业务结果及效果相同。
重放的 Outcome、业务 Reason、StateVersion 与原正式结果相同；IsDuplicate=true、返回 Events 为空。原结果若有其他业务字段也不能静默忽略：当前 CookingRecipeCommandResult 还有 Supply，本次 Pickup fixture 应保持双方均为 null。
缓存 Executed 路径保留原 wire disposition/reason；原生 Duplicate 路径如有不同 wire reason，原样记录，不能伪造为缓存结果。

权威效果没有重复。
在验证 scope 的 authority 切片里，按实际 DomainCommandId＋ActorId 关联事件。该命令事件身份/数量不增加，目标 item 和独立 hand 索引不因 retry 再变。当前成功 Pickup 原本应有的业务事件也不能缺失，不能用“前后都是零条”假装证明幂等。
允许无关 Tick 推进全局 StateVersion/LogicalTick；不比较整个世界完全不变。

调用顺序仍是：
正式竞争结果 → 权威 OWN/REJECT → pickup 客户端投影收敛 → 原胜者精确重放 → 正式重放结果及当前绑定复核 → 权威 retry 切片 → IDEMP。

adapter 在每个相关 await 后检查绑定，并把支撑判断的观察保存在既有 Cuts/事件中。不能仅保存一个“检查过=true”后让 evaluator 盲信。实际 wire correlation 对公开接口不可见时仍为 null，不用 CallId 或猜测的 cmd-N 填充。

四、C13-REJECT 也按实际 DomainCommandId 归因

网络事件的 Command.Value 是领域映射 ID，不是 wire BusinessId。REJECT 和 IDEMP 必须采用相同的关联原则：

在匹配的 authority scope 内：
event.Command.Value == observation.DomainCommandId
并且 event.Player.Value == observation.ActorId。

Offline 的实际领域 ID 恰好与业务 ID 一致，仍然读取已有真实 DomainCommandId，不靠 fallback 补值。缺少 ID 时不能把“按错误 ID 找不到事件”当成“没有副作用”。

保留 B1 的判定边界：

缺身份、缺正式终态或事实不足：相关检查 Undetermined；已启动但不能完成目标的 run 不能 Passed。
已知且可靠的拒绝方成功事件/持物矛盾，即便另一调用尚无终态，仍保留确定违规。
错 scope/session/generation 或响应身份不匹配：停止本次关联和新动作，记录绑定/协议/测试证据错误；不能拿别的调用补齐。
测试器发错 payload 不属于有效精确重放，应在发送前拒绝或停止；不能将其包装成产品幂等 bug。
在正确身份和实际相同 payload 下，正式结果变化、重复业务事件或目标所有权再次变化，才是这里能够证明的规则失败。
若刻意用同 stable ID、不同 payload 检查冲突，按现有冲突事实记录，不把 Conflicted 当成功 replay；本次不新增这种玩法 flow。

五、in-flight duplicate 不等于缓存重放完成

Map 对尚无 cached terminal 的重复请求会继续走正式映射/等待路径。排队、Arm/ACK、客户端投影、原生 Duplicate 字样本身都不是完整执行证明。

首个固定 flow 已等待原胜者结果，所以它验证的是完成后的精确重放。对于碰到的 in-flight 情况：

在原预算内等待各自正式结果，保持不同 CallId 和真实返回事实；
获得正式 Duplicate＋有效业务 Result 后，才能按同一组身份/结果/效果条件评估；
无 Result、超时、取消、断线或结果不明，保持 Unknown/Undetermined 或实际协议拒绝；不复制原调用结果冒充该调用返回；
不因等待失败重置预算、自动重发或声称命令未执行。

不需要为此增加一个长时间的 in-flight 并发场景作为本轮隐藏前置。
