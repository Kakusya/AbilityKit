三个阻塞问题和最小修订

B1：没有取得业务终态，会被误报成产品规则失败

FixedFlows 在验证 pair 的终态完整性之前评估 OWN/REJECT；REJECT 又把“没有恰好一个 Rejected 结果”直接判为 Failed。

现有 Timeout 控制恰好会产生两个 Unknown、BusinessResult=null 的调用。于是：

OWN 为 Undetermined；
REJECT 却为 Failed；
编排者把它记为 ProductFailure，最终产品 Verdict=Failed。

这时只知道测试等待超时，并没有证明游戏拒绝逻辑出错。现有测试只检查 Verdict 不是 Passed，因此漏过了误分类。

位置：
FixedFlows.cs 25–35(https://github.com/Kakusya/AbilityKit/blob/b387179fd4ae60339c3aa7f3a6efb3f12f7a976a/src/AbilityKit.Game.Cooking.FlowAcceptance/FixedFlows.cs#L25-L35)；

修订：

“拒绝数量违反规则”必须建立在足够的正式业务终态上；缺失终态时返回 Undetermined。
超时/协议拒绝/准入拒绝仍保留各自真实原因，不伪装成领域拒绝或产品 bug。
不要简单地在所有规则前一刀切丢弃不完整结果：已观察到的独立手槽矛盾、拒绝方真实成功副作用等，仍然可以构成确定的 ProductFailure。
加强现有 Timeout 子用例：要求产品 Verdict=Undetermined、无 ProductFailure、保留超时原因且正常归位。已有真实产品失败＋清理失败控制继续保留。

B2：错误事件类型携带的 payload 也能充当完整证据

collector 目前只检查某些 Kind 的必需 payload 是否存在，没有禁止其他 payload。合法序号的 StepStarted 如果携带 Command 或 Observation，会被接收并索引；HasRequiredEvents 随后可以把它当成正式命令/状态证据。

这违反了原合同中“payload 与 Kind 匹配，其他 payload 为空”的要求。

位置：FlowEventCollector.cs 39–70(https://github.com/Kakusya/AbilityKit/blob/b387179fd4ae60339c3aa7f3a6efb3f12f7a976a/src/AbilityKit.Game.Cooking.FlowAcceptance/FlowEventCollector.cs#L39-L70)。

修订，在入队和索引之前验证：

CommandObserved：只有 Command 非空，CallId 匹配。
RoleReady / StateObserved：只有 Observation 非空。
RuleChecked：只有 Check 非空。
StepStarted / RoleFaulted / RoleStopped：Command、Observation、Check 全部为空。
不合格记录锁存 evidence incomplete；不能进入命令/观察索引。

把 wrong-kind payload 反例并入现有 collector 测试，确认它不能满足 HasRequiredEvents。无须新增事件类型或改 DTO。

B3：执行结束后的取消可能仍返回 Passed/0

最后一次检查调用方取消发生在玩法执行结束附近。随后 cleanup、collector flush 和报告发布使用独立 token，但最终通过判定和发布读回没有再检查原调用方 token。

因此在 flush 或报告 I/O 期间收到 Ctrl+C，有可能最终仍留下 Passed result 并退出 0。

位置：FlowOrchestrator.cs 137–201(https://github.com/Kakusya/AbilityKit/blob/b387179fd4ae60339c3aa7f3a6efb3f12f7a976a/src/AbilityKit.Game.Cooking.FlowAcceptance/FlowOrchestrator.cs#L137-L201)。

修订：

明确以最终发布/读回确认作为完成点；在此之前观察到调用方取消，应锁存为执行环境/调用取消事实，不能整体 Passed。
清理仍用独立 token，不因原 token 已取消而跳过。
生成最终状态前，以及发布等待返回后，检查取消是否已发生。若已经写出但尚未接受的 Passed marker，沿用现有不完整结果处理，不让调用器把它当成功交付。
已经完成的玩法结果、command effects 和真实证据保持原样；不能把取消改写成产品失败或撤销已提交动作。
完成点之后的取消不追溯改写已完成测试。

在现有取消/报告控制中增加一个确定性的 late-cancellation 子场景即可，例如报告等待期间取消调用 token。无需靠长时间 sleep 制造竞态。

最小初始化顺序：

child 首先在固定 10 秒启动预算内等待一条有界 NDJSON Initialize，读取前就限制消息大小；未收到、格式错误或 EOF 则退出，不能无限等待。
第一条要求 schemaVersion=1、ControlSequence=1、RoleId 与 --id 相同、Init.RoleId 相同、唯一合法 ControlId，其他动作 payload 为空。校验非空合法的 RequestId/RunId/AttemptId 和有效 generation，固定完整 RunIdentity，随后消息不得换 run/attempt/generation；第二次 Initialize 拒绝。
server 的 Init 使用已批准 fixture，ActorId/Endpoint 为空。创建真实 ET/session，使用 loopback 地址和构造参数 port=0，再调用现有 listener.Start()，从实际 Endpoint 回报绑定端口，不预留后关闭端口。这里更正一个签名细节：当前源码是构造器接收 port，Start() 无参数，并不存在 Start(0) 重载。
server Ready 回传真实初始 authority 观察和实际 endpoint。
父进程再初始化 client-a/A、client-b/B；client Init 的 Fixture 为空，Endpoint 为刚才的 loopback 端点。
client 通过实际 Join/session/baseline 建立当前绑定，Ready 带真实 client 观察。父进程核对 server instance/scope 和各 client 自己的当前 connection generation；没有当前已安装 baseline 就不能 Arm。
按已接受 Arm/Release/Observe/Stop 和 ReplayOfCallId 合同推进。ControlId 与 replay CallId 的映射保持 amendment，不另加字段。

RoleReply.HostSequence 是全部回复的序列；嵌套 FlowEvent.HostSequence 是事件流的序列，分别连续递增。Armed 等无事件回复不能造成 collector 事件序列缺口。父进程不能补造缺失事件来“填序号”。

职责与出口：

pipe reader 只做有界读取/校验/入队；游戏初始化、ProcessOwnerFrame、观察和释放均在 child owner。
server 只有 ProcessOwnerFrame 驱动现有权威，不额外 Tick；网络 command batch=0。等待 stdin 或 client 就绪时也必须保持 owner pump 推进，否则真实 Join/ACK 会因无人处理而卡住。
stdout 仅 RoleReply NDJSON，stderr 为有界诊断。只有父 collector 写最终 events.jsonl 和报告。
返回 0 仅表示收到 Stop 后本角色正常收尾；1 为运行故障；2 为启动/协议前置拒绝。child exit 0 不是玩法通过，父进程仍要检查全部规则、证据、归位。
提前 EOF、崩溃、错绑定或取消停止新动作，保留已知终态；按原预算关闭本次资源/reader。父进程记录 native exit，未知退出不得伪造 Stopped。
client 取消等待不撤回已发送 command；意外换 scope/重连仍停止本轮，不新增恢复框架。
Stop/关闭使用独立收尾预算。Session.Dispose 不代替 ET authority 的释放；在合法 idle-owner 点分别释放本次拥有的对象并结束 reader。现有客户端内部 15 秒等待由外层已批准的更短 token 限制，不改产品超时。
