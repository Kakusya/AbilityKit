OfflineFlowAdapter 的内部 owner-only 操作固定为：

SubmitGroup：逐项调用 TryEnqueue，无中途 Tick/await；
PumpOwnerOnce：一次 host.Tick；
CaptureAuthority：复制权威 item、独立 ItemInHand 及相关 command events；
终态汇合：Admission.TerminalDisposition、Tick().Dispositions、DispositionHistory；故障/结束时再读可用的 FinalDispositionHistory。
按 call/correlation 去重同一终态的多处观测，不去重掉真正不同调用。

DrainNewTerminalDispositions 是网络通知队列，不能作为 offline 的唯一来源。准入拒绝且没有 terminal 是“没有进入领域执行”的已知结果，不无限等待不存在的 terminal。

offline 同组新命令使用同一个合法正 SimulationBatch；新组大于 LastCommittedSimulationBatch。既有 owner 会按规则排序，报告应称“同批竞争”，不是多线程同时修改领域。

network 命令的 SimulationBatch 必须为0，由 SessionHost 映射。不要把 offline 的正 batch 直接发上网。预期 domain ID 使用现有：
CookingNetworkWireCodec.DomainId(string instance, CookingLevelScope scope, PlayerId participant, string stableId)。

Client.SendCommandAsync 内部生成 wire correlation，调用者不能伪称自己设置了它。CallId 关联返回任务；真实 wire correlation 若公开入口不可见就为 null，服务端观察到的 correlation 则原样保留。

ReplayAsync 必须保存原始命令，包括 ExpectedItemVersion、offline 原 batch、network batch0及所有其他 payload。不能根据最新 snapshot 重建重试。Drop 使用新 BusinessId、新观察到的版本以及已配置合法槽位。

四、S2 的进程与控制协议

一个短生命周期父编排进程，管理三个本次新建子进程：server、client-a、client-b。旧 RichRunner 的“本地 Chef＋远端 Partner”不直接算这项验收。

使用同一个新 CLI 的私有 host role 入口。父子通过重定向 stdin/stdout 的有界 NDJSON 控制，不用 MCP/HTTP 服务。游戏命令仍经客户端 v3 网络传输；控制管道不发送“安装此世界 snapshot”。

五、所有权、取消和提交语义

游戏可变状态的唯一 writer 仍是现有 ET owner。初始化、推进、观察、Dispose 均在创建线程且合法 idle 点完成。
collector/report 在自己的 I/O 路径工作，不能回调修改领域；owner 不等待磁盘写入。
不对触碰 host 的 continuation 使用 Task.Run 或 ConfigureAwait(false)。
每次 await 后重验取消、run generation、角色存活、scope；network 还核对 session instance/connection generation。首版遇到意外重连/换 scope 即停止该 flow，不扩成恢复产品。
取消 SendCommandAsync 只取消本地等待，不撤销已经发出的命令。结果未知时保留未知，并在有界归位中读取可用服务端事实，不能填“未执行”。
fixed-step 失败不回滚之前已提交的 command effects/event/Executed terminal。保留这些事实及故障，不伪造正常完整 capture。host 已 faulted 时保存最后有效 cut、终态历史和可用诊断；Available=false 明确表示当前完整观察不可得。
CloseAsync 必须幂等，第二次返回同一收尾结果；所有本次 task/pipe reader/事件订阅结束后才退出 SingleThreadOwner 场景。generation 退役后晚到回调不得写下一 run。

六、五张规则卡的修订建议，均不代替 Owner 批准

C13-OWN：
保留提交点唯一归属；authority 使用独立手索引＋item location。fixture 必须证明两角色最初空手、具资格、合法可达。客户端只验证自己的正式投影，不冒称校验服务端内部索引。

C13-REJECT：
不固定失败原因为 ItemStale。当前空间校验可能先得到 TargetOutOfRange。类别表达“合法竞争失败不产生该命令成功副作用”；具体 fixture 的合法原因集合由源码对应路径列明。全局状态/version 改变不算拒绝方副作用。

C13-IDEMP：
删除“全局 event 水位不得变化”的歧义。固定 Tick 自己也会推进全局 sequence/version。检查原 command 的业务事件身份/数量、重复返回不产生新业务事件、目标 item/独立手槽不因 retry 再变。重试必须保留原 batch/version/payload；新操作不能借原 ID 冒充 retry。

C13-CONVERGE：
用当前 session/scope/generation 的实际安装完整 baseline，recipe version 至少达到目标 fence，并匹配所选 item/手持字段。允许更高 version，不要求全局快照逐字相等。
必须在 pickup 后、下一次改变该物品之前验证 pickup 收敛。不能用最终 Drop 的收敛补证明 pickup。
IsSynchronized 不是当前采样 baseline 的精确 ACK/Ready 身份证明。初始连接按现有 Join/baseline/Ready 路径；首版不新增目标 ACK 追踪能力，结果写“已安装目标投影收敛”。

C13-COMPLETE：
这是执行完整性/收尾条件，与产品规则分开记录。已确认产品失败＋后续崩溃可同时存在；没有结果、证据不全或归位不明不能 Passed。
测试 flow 完成不等于餐厅自然经营成功。最小拾取测试结束按测试会话释放，不调用 TryFinishService 冒称完成整个关卡。

规则审批卡仅需 ID/version、语义、适用 fixture/mode、允许参数范围、正反例、Owner 决定引用。S1 使用 OWN/REJECT/IDEMP/COMPLETE；CONVERGE 在 S1 标不适用，S2 才消费。现在全部仍是 Draft。

首个 flow 定稿：
初始化 → 初始观察/联网就绪 → 两动作 barrier → 两正式结果 → authority OWN/REJECT → network pickup 收敛 → 胜者精确 retry → IDEMP → 收尾。
把 Drop 从这条首例移到独立 pickup-drop-one-item/v1：单角色 Pickup → 观察/必要收敛 → 新 ID及新版本 Drop → authority及必要客户端目标观察 → 收尾。这样复用是实在的，也不会把两个目标的证据窗口混在一起。

七、预算、证据与归位

建议提案值：

startup 10秒、每步骤10秒、convergence 10秒；
overall 120秒，包括 startup/执行/归位/结果发布；
预留 reset 10秒、publish 2秒，活动工作最迟在 overall−12秒停止。
每个局部等待取“自身预算与剩余预算”较小者。客户端原15秒内部超时不改，以外层 cancellation 限制等待。Owner 可批准一个参数范围，不需每次数据变体重批；收紧预算得到的超时也不能无证据归因为产品 bug。

collector queue 256、单条事件64KiB、首例总4096事件/8MiB、每角色 stderr 256KiB，作为工程初值而非性能承诺。超限前记录限制；必要事件写入失败在带外状态锁存 evidenceIncomplete 并停止新动作，不能依赖把“溢出事件”塞入已满队列。正常 debug 截断可提示；验收事实丢失绝不 Passed。所有 cap 调整须说明原因，不能默默绕开失败。

失败先固定首次 cut/事件位置，然后：
停止新动作/扰动 → 取消并有界收集等待中的调用 → 关闭客户端 → server 有界处理断开/清理 → session dispose → idle-owner host dispose → 等待本次子进程/reader退出 → collector flush → 发布 failure/report/result。
收尾使用独立 token。不得使用已经取消的执行 token 立即跳过清理。

父编排者只管理自己启动且身份仍匹配的进程。优先正常关闭；若需要强制终止，只能作用于已确认的本次子进程并记录 forced termination，不能全局 kill dotnet。归属/退出未知则 Cleanup=Incomplete，阻塞 fixture 复用。S1 同进程 owner 若卡死，由实际调用器的有界进程监督处理；不存在终态结果就按不完整执行记录，不能承诺进程自己总能写出报告。

request/result/event 的测试 schemaVersion 首版固定1，和游戏 wire v3分开。使用 BCL JSON、文本枚举、必需字段/上限验证，未知版本或未知动作拒绝。记录只含稳定值，不序列化 Entity/内部集合或凭据。原始业务 wire 使用现有 codec，不另造 serializer。
当前 source/version、dirty、配置、命令、规则/flow版本、必要事件及终态足够；不增加编译器输入追踪或整套 SDK/DLL 归档。

十、S3 一次提交/等待/返回的真实试点

当前 dotnet --version shell 等待只证明普通子进程完成返回，Orca advertised capabilities 不等于新玩法自动唤醒已经接通。

可实现的首路径：
调用器启动 run 命令并等待进程 → 编排者内部完成全部等待 → 完整写出 result 并退出 → 同一次工具返回小摘要 → agent读取对应result/failure包。

以后用一个短成功flow和一个故意失败flow实测：

分别只提交一次；
等待期间模型不反复发 status；
结束后获得匹配request/run的结果与真实退出；
失败只读取小失败包；
另测进程无result退出，调用器必须报告不完整。
记录实际工具是否yield、如何等待、是否真的产生完成通知。若只能一个显式wait，则如实采用，不冒称后台自动唤醒；文件本身不唤醒agent。
