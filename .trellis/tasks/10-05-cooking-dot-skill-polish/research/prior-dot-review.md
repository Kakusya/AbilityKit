二、明确结论

还不是一份可以放心交给新对话，可靠完成自主交付和中断恢复的成熟 skill。

更准确的定位是：一份边界认真、风险意识较好的工作流规范草案。它已经说明了很多“什么时候必须停”，但还没有把关键环节全部写成新执行者能够一致执行、核对和恢复的操作约定。

问题不是“没有脚本，所以不算技能”，也不是一定要再造调度器。文档型 skill 完全可以成熟。但这份实现仍让执行者临场决定几件关键事情，而这些决定会影响重复执行、恢复和交付状态。

此前“15/15 静态情景 Passed”证明的是：审阅者能依据规则推导出看起来合理的动作。它不证明新对话真的能恢复 Run、识别检查点或完成自动交付。归档记录自己也明确将这些路径标为 NotRun。

三、实质问题与最小修改建议

恢复记录有字段清单，却缺少确定的发现和读取约定

位置：recovery.md 第3、11–18、22–23行。

现在要求保存 recovery index、append-only 意图和回执，然后自动寻找唯一未完成流程。但没有固定：

索引文件名和版本。
稳定的流程 ID。
同一流程在多个 worktree 中出现时，怎样去重。
哪一份记录是权威。
意图文件已写入、索引尚未更新就崩溃时，怎样恢复。

具体触发：两个 worktree 都包含同一个 task 的 research，一份较新、一份较旧。新会话到底应当识别为“一个流程的两份副本”，还是“两个待 Owner 选择的流程”？目前需要猜。

已有机制：Trellis 的 io.py 第107–147行已有临时文件写入后替换的工具，可以复用。它不是整个工作流的事务系统，也不能据此宣称断电安全。

最小修改：增加一个 task 内的检查点模板，固定入口、flow ID、操作序号、权威位置和写入顺序；明确以“进程崩溃”为最低恢复模型。不要改 task schema，也不要建设新的数据库或调度服务。

依据：恢复记录与发现规则(https://github.com/Kakusya/AbilityKit/blob/86d44e8f8a6ac2ca958f4c453555817da7b1f15c/.agents/skills/cooking-dot-workflow/references/recovery.md#L3-L27)。

“唯一调度者”的恢复依赖尚未验证，不能只在出事时再发现

位置：recovery.md 第25–27行。

它要求证明旧主控已退出，再通过 Orca 支持的操作重新绑定。这是正确的安全要求。但是，当前实现没有证明实际 Orca 能完成这个动作。

已有机制：Trellis 的 active_task.py 第732–758行保存的是“每个会话的活动 task 指针”，不是独占调度权。两个会话各自有指针，并不等于只有一个会话有派发权。

具体触发：主控派发 worker 后崩溃。新对话能找到唯一流程，worker 仍在运行，但无法证明普通 Run 支持接管。此时技能只能安全停止，不能完成所期待的恢复。

我不建议删掉这个停止条件；建议把能力核验提前：

首次派发前，确认正常 Run 的恢复方式。
记录用什么实际返回值证明唯一调度权。
确认两个恢复者同时进入时，谁会被拒绝。
若能力不存在，明确将本次流程标为“跨会话恢复受阻”，不要仍对外承诺自动恢复。

这属于未验证前提，不是已经证明 Orca 没有该能力。安装记录第35行明确将真实 crash/rebind 标为 NotRun。

dot 等待规则有两处容易产生不同执行结果的歧义

位置：dot-dialogue.md 第10、15、24–28行；recovery.md 第27行。

第一处：最多一次补问，是否包括“请明确确认”？
第10行允许对含糊回复继续求确认；等待表只限制 reminder。执行者可能把第二次、第三次确认解释成“不是提醒”，从而绕过一次补问上限。

第二处：超时后才看到有效回复，怎么办？
例如主控第20分钟崩溃，第二天恢复，发现 dot 已经明确审阅同一个 SHA：

回复是在第25分钟发出，只是后来才看到。
回复是在第40分钟才发出。
页面不能可靠提供发出时间。

“有效回复即可退出等待”和“过期立即暂停”没有说明这些情况的优先级。

最小修改：

同一请求的提醒、追问、确认共用一次补问额度。
分开回复时间和观察时间。
明确及时回复但迟读、真正迟到回复、时间未知三种处置。
定义超时后的重新开启方式；若开启新请求，使用新 ID 并链接旧请求，保留旧超时，不能偷偷刷新原预算。

依据：dot 回复与等待规则(https://github.com/Kakusya/AbilityKit/blob/86d44e8f8a6ac2ca958f4c453555817da7b1f15c/.agents/skills/cooking-dot-workflow/references/dot-dialogue.md#L8-L28)。

Trellis 的“结束会话”与本流程的“完成需求”需要明确隔离

位置：SKILL.md 第17、33–34行；trellis-finish-work 的归档步骤。

技能说复用 Trellis，这是对的。但现有 finish-work 会将当前任务送去归档；实际 task_store.py 第1317–1352行会设置 completed，第1428–1457行会清除会话绑定并移动任务。这个命令本身不会核验 dot 接受和合并后集成结果。

具体触发：dot 超时，主控准备结束本次会话，顺手调用通用 finish-work。一个“等待审阅、应能恢复”的流程可能被当成完成任务归档。

这不是已经发生的故障，而是新 skill 与已有收尾机制之间缺少明确适配。

最小修改：在技能内增加几条具体调用条件：

暂停、待审、调度权未知、集成失败时，不调用完成/归档路径。
结束当前会话只保存交接，不完成需求。
只有记录中具备指定的接受、合并和集成证据，才允许进入 Trellis 归档。
复用现有命令，不修改通用 Trellis 框架。

依据：实际归档实现(https://github.com/Kakusya/AbilityKit/blob/86d44e8f8a6ac2ca958f4c453555817da7b1f15c/.trellis/scripts/common/task_store.py#L1317-L1457)。

自动合并之后才关 Issue，缺少“防止合并顺带关单”的检查

位置：SKILL.md 第32–33行。

规则要求先合并，再在实际合并版本上做集成检查，成功后才关闭 Issue。这个顺序合理，但没有规定如何避免 PR 的自动关闭关联提前关单。

具体触发：PR 使用了合并即关闭 Issue 的关联方式；合并完成后，集成检查失败，但 Issue 已被提前关闭。

最小修改：

集成通过前使用不自动关单的关联方式。
合并前检查会触发自动关闭的 PR/提交关联。
如果无法在授权范围内排除提前关闭，暂停合并。
集成通过后显式关闭对应 Issue，并读取确认。

这是一处缺失的协议检查，不是声称当前 PR 已配置了自动关闭。

依据：合并与关闭顺序(https://github.com/Kakusya/AbilityKit/blob/86d44e8f8a6ac2ca958f4c453555817da7b1f15c/.agents/skills/cooking-dot-workflow/SKILL.md#L30-L34)。

正常流程需要一份真正能照着走的交接清单

位置：SKILL.md 第15–25行，SOP 第22、30–35行。

现在必要元素大多存在，但分散在多个段落。“读取每个 Issue”之后直接进入 dot 和 worker；新需求没有现成 Issue 时，创建、填充、绑定和派发的顺序不够明确。规划请求与最终接受请求也没有各自的最小示例。

建议只补一条短的主路径：

需求批准 → 提交可读的需求/源码 → dot 规划 → 保存并核对 Trellis 计划 → 创建或核对需要的 Issue → 进入执行状态 → Orca 派发 → 实际证据与独立审阅 → dot 精确 SHA 接受 → 合并前检查 → 合并后集成 → 关单和归档。

同时给两份小模板：

请求模板：规划还是最终审阅、请求 ID、SHA、范围、问题、证据。
决策记录：已接受／需修改／被阻塞、阻塞项、接受的 SHA、下一步允许做什么。

小任务仍可按 SOP 不开 Issue，不能为了填流程强制增加工单。技术规划已经受托，也不应再沿用通用技能的提示，反复让 Owner 批准相同需求。

五、按优先级排序的最小修订与验收

第一优先：让停止之后真的能恢复。

补稳定检查点模板、同流程副本识别、写入/读回步骤。
补普通 Run 恢复能力核验和独占权证据。
补迟到回复、补问计数和超时后重新开启规则。

第二优先：封住错误完成的入口。

增加 Trellis finish/archive 适配条件。
增加合并前自动关单检查。
明确冻结的代码候选与后写的审阅回执/归档证据如何分开保存，避免把新提交误套旧接受。

第三优先：打磨入口与渐进披露。

一份主路径清单、两份交接模板。
删除 SOP 与 references 的重复细则。
保留运行时动态发现 Orca 命令，不复制整本手册。

必要验收应是可观察的操作结果，而不只是再做一次规则问答：

全新对话处理一个已批准 Cooking 小需求：无重复需求审批；需要 Issue 时只创建一个；一个合法主控和有界 worker。
发送成功但回执丢失：恢复后不重复发送或创建。
检查点写入中断、索引落后、跨 worktree 副本：能确定恢复或明确阻塞，不重复副作用。
两个新会话同时恢复一个孤立 Run：最多一个能取得派发权；能力不支持时不得宣称恢复成功。
dot 超时、含糊回复、迟到回复、旧 SHA 回复：预算、补问次数和接受判断都符合明确规则。
超时后结束会话再重新加载：任务仍未完成且可发现，不被通用归档误收尾。
合并后集成失败：Issue 保持未完成，task 不归档；恢复后只执行未完成的后续步骤。

这些应在另行批准的最小试跑或隔离场景中验证，不借机扩大到新调度平台、其他示例或 Unity。

最终判断：保留现有骨架，重写少量操作约定并补真实流程验收，比继续堆更多原则更有价值。当前我不为“成熟、可可靠自动恢复交付”背书；我认可的是它已经建立了较好的安全边界和部分可复用基础。
