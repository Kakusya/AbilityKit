## 目标

在 Cooking 单一产品范围内，先收敛一条代表性的产品闭环，再为首个“两名玩家 + Host/Client + 通用 Network.Runtime/Transport”的多人网络纵切建立模块化规划。规划必须明确产品边界、权威归属、模块依赖方向、网络消息边界、验证出口和 Unity 后置条件，避免先做单机后整体重写，也避免为了赶网络而把 Cooking、ET、KCP 和 Unity 互相耦合。

## 本轮已确认的产品化方向

### 只推进 Cooking

- 当前主动规划和施工范围只包含 Cooking；
- Shooter、MOBA 以及其他示例模块不进入本轮主动功能开发；
- 其他模块只保留维持 Cooking 所需的共享框架依赖和回归门禁，不把它们作为并列产品主线；
- 文档清理阶段需要把其他模块降级为历史背景、维护约束或明确的后续范围，避免继续污染 Cooking 路线。

### 两条运行线与后续 Unity 接入线

当前采用“共享核心 + 两条运行线 + 后续 Unity 接入”的结构：

1. **单机运行线**：在无网络传输的情况下运行当前已经确认的 Cooking 功能；
2. **局域网联网运行线**：让同一批当前功能经过 Host/Client、通用 Transport、命令 ingress、权威 Tick 和状态同步；
3. **Unity 接入线**：后续作为独立的宿主/表现接入，消费稳定的纯 C#、运行时和网络契约。

两条当前运行线不得各自实现一套玩法。它们必须共享：

- Cooking 领域规则；
- 状态模型；
- 固定 Tick；
- 命令语义；
- 结算合同；
- 稳定身份和生命周期边界。

局域网纵切只覆盖已经确认的 Cooking 功能，不因为接入网络而临时新增玩法。业务失败已明确排除；基础积分/星级后来通过独立 task 实现并接入网络共识，收益、评价和伙伴成长仍必须各自立项。

首个联网纵切的技术范围是：

- 两名玩家；
- 一个 listen Host 和一个 Client；
- 当前已有的 Match/Level/厨房功能；
- 通用 Network.Runtime/Transport 进入真实传输路径；唯一使用通用 LiteNetLib reliable-UDP adapter 作为真实网络传输（不使用 TCP），不为 Cooking 保留独立 UDP 实现；
- Host 持有唯一玩法权威；
- 客户端发送权威命令，接收权威快照/结果；
- 使用固定 Tick 和稳定仲裁；
- 以当前已有的番茄蛋花汤闭环为验证载体；
- 不通过联网任务扩张当前业务功能。

### 模块化边界

必须保持以下依赖方向：

```text
Cooking Domain
    ↑
Cooking Application / Session
    ↑
Host Runtime / Client Runtime
    ↑
Protocol Contract / Codec
    ↑
Generic Transport Adapter
    ├── LiteNetLib reliable UDP (唯一真实网络 Transport)
    ├── InProcess (用于本地测试与 Host 本地玩家)
    └── future interchangeable transports
```

实际实现时依赖方向应表达为“上层依赖稳定契约，下层提供实现”：

- Cooking 领域不得引用具体 Transport、Socket、ET 或 Unity；
- 具体 Transport Adapter 不得引用 Cooking 领域实体内部结构；
- 网络协议只传输稳定 DTO、命令、事件和快照，不暴露领域可变对象；
- ET 只承载宿主生命周期、Tick 调度和线程边界，不复制第二份 Cooking 权威状态；
- Client 不拥有玩法写权限；
- Unity 后续只消费宿主/客户端输出，不重写规则；
- 单机与局域网两条线共享玩法核心，不以复制代码换取短期进度。

### Unity 后置

- 当前只规划纯 C# Cooking、通用 Transport Host/Client、协议和网络验证，不规划 Cooking Unity；
- Unity 暂不纳入当前规划和施工；未来是否重新开启另行审议；
- Unity 接入必须消费已稳定的模块契约，不反向改变领域规则和网络权威。

### 小关自然完成、积分与星级

- 业务失败与网络/运行时终止严格分离；
- 小关不设置必须达成的业务目标，也不设置业务失败条件；
- 小关按既定营业时间和收尾规则自然完成；
- 完成后只累计积分，并把积分映射为面向玩家展示的星级；
- Host 关闭、连接中断或 Match 解散只属于网络/运行时终止，不生成小关失败结算，也不生成低星完成结果；
- 基础积分与星级已通过独立 task 实现并接入同机 Host/Client 快照共识；
- 当前代码中已经存在的失败重开合同暂作为兼容能力保留，但正常产品流程不主动触发业务失败；是否退役另立清理任务审议。

第一版积分与星级合同：

- 每个订单从配置读取固定基础分；
- 成功提交订单时只计分一次；
- 未完成或超时离席的订单计 0 分，不倒扣；
- 本关总分为全部有效订单积分之和；
- 总分通过关卡配置的阈值映射为 0–3 星；
- 0 星仍表示自然完成，不构成失败；
- 星级只用于结果展示，不阻止进入下一小关；
- 第一版不影响解锁、Buff、装修、存档奖励或其他进度；
- 第一版不加入速度倍率、连击、菜品质量、收益或额外奖励。



## 已确认决定

### 大关与递进小关

- 一个大关包含若干小关；
- 大关内的小关是互相递进的关系；
- 玩家从初始小关开始，在同一家餐厅和同一份大关进度上持续装修、优化和推进；
- 后续小关不是重新创建一份彼此独立的餐厅；
- 小关身份可以变化，但大关内持续演化的餐厅状态需要延续。

### 下一小关前的选择

在递进到下一小关前，玩家可以选择：

- 装修方向；
- 新道具 ID；
- 新 Buff；
- 其他后续确认的餐厅优化内容。

这些选择的准确身份、持续范围、生成规则和状态归属尚未确定。

### 不预设独立关间准备模型

- 不因为存在两个小关之间的选择过程，就直接规定一套与小关并列的“关间准备”业务模型；
- 准备和选择应从“小关递进、同一家餐厅持续优化”的产品语义出发；
- 它们最终如何归属于小关生命周期、餐厅运行状态或其他业务对象，需要在具体局内规则明确后决定。

### 小关成功检查点

- 不能在小关运行中保存检查点；
- 不能在准备或选择过程中保存检查点；
- 小关失败不保存检查点；
- 失败或中断不得覆盖最近一次成功检查点；
- 只有小关成功结束、结算和状态收口完成后，才保存新的检查点；
- 检查点表示最近一次成功小关结束后，大关内餐厅已经确认的累计进度和稳定状态；
- 准备阶段作出的装修、道具和 Buff 选择，只有在对应小关成功后，其最终结果才进入新的检查点。

### 跨小关延续方向

- 成功小关之间可以保留食材、半成品、容器内容和未完成加工；
- 未完成加工的进度需要保留；
- 工位升级时，未完成加工自动迁移并保留进度；
- 失败现场不进入检查点，失败重试按关卡定义的标准初始供应重建；
- 装修、道具和 Buff 如何影响这些状态，仍需继续讨论。

### 顾客、餐桌与 NPC 小伙伴

- 采用“可见顾客 + 自动服务 + 餐桌控制客流”的半抽象顾客方向；
- 顾客真实进入餐厅并使用玩家摆放的餐桌，使餐厅经营结果得到真实、持续的可见反馈；
- 入座、基础点单、普通送餐、结账和常规清洁等高频琐事不默认要求玩家逐桌操作；
- 餐桌是接待容量、客群结构、订单波峰和空间规划的一部分，不只是装饰或线性收益加成；
- 玩家仍以做菜、协作和厨房工作流优化为主要局内操作；
- 引入 NPC 小伙伴承担接待、打扫等前厅事务，使自动化不只是后台数值，而是持续可见的正面反馈；
- NPC 小伙伴采用少量固定伙伴的方向：每位伙伴有名字，会长期成长并陪伴同一家餐厅；
- NPC 小伙伴不是可不断招聘、替换并追求数值配置组合的普通员工，也不构成另一套需要持续维护的人力资源系统；
- 当前已收敛：玩家不承担常规前厅微操；未满足订单计 0 分、不倒扣且不导致失败；伙伴成长只在小关内有效并在下一小关重置；伙伴固定岗位且不由玩家局内指派；第一项成长能力为完成 3 个伙伴任务后解锁洗碗耗时减半。装修/餐桌布局与伙伴能力的联动不进入首个成长纵切，后续另行审议。

### 代表菜与首个闭环

- 首个局内做菜闭环的代表菜选定为**番茄蛋花汤**；
- 首个闭环必须同时覆盖多输入、半成品、持续加工和装盘四项基础规则；
- 预处理（切番茄、打蛋）消耗原物品，生成新的半成品物品实例，不追加状态；
- 多输入加工由玩家显式启动，配方自动识别；
- 配方中的水视为默认供应，不占物品和容器容量；
- 订单要求“碗中的汤”，提交对象是碗（含汤）；
- 顾客自动入座后由 NPC 小伙伴前往询问，再生成订单；NPC 询问是订单进入订单簿的触发点；
- NPC 询问走到桌边后停留若干 tick 完成，期间该 NPC 被占用；顾客久等不惩罚，只影响订单节奏和餐桌占用；
- 脏碗由 NPC 小伙伴空闲时清洗，清洗占用若干 tick；营业时间里顾客按配置间隔持续到店；
- 玩家基础动作集为七项：拾取、放下、放入、取出、启动加工、倒出、提交，均为权威原子命令；
- 加工时长、询问与清洗 tick 数、营业与收尾时长、干净碗总量等数值一律由配置定义；
- 小关分为营业时间和收尾时间；收尾时间不来新顾客，必须等全部顾客离席后才结束；顾客吃完会走，超时也会走；
- 小关按时间结构走完且全部顾客离席后自然完成；不设置目标或业务失败；
- 收尾时未做完的订单随顾客超时离席记为未满足，影响评价，但不影响小关成功；
- 提交后顾客短暂占桌用餐，随后离席并产生收益与评价，餐桌释放；
- 小关结算以订单固定基础分累加为总分，并按配置阈值映射 0–3 星；该第一版合同已经实现并验证；
- 煮制到点完成时输入保留在锅中，锅切换为“已完成”状态，成品在倒出时才生成；
- 首个闭环不包含过度加工、烧焦或失败产物；
- 配方外物品在放入阶段即被拒绝，不进入启动校验；
- 干净碗数量有限，提交后碗变脏，由 NPC 小伙伴清洗后归还干净碗池；
- 从锅倒进碗时生成独立的“蛋花汤”物品实例放进碗中；
- 锅允许放入哪些物品由锅自己的配置定义声明；
- 锅和碗的容量由配置定义，同类物品不堆叠，每个物品独立占位；
- 固定工位：首个闭环需要砧板和灶台，动作必须在对应工位上执行；一个工位同一时刻只进行一个加工；
- 预处理（切番茄、打蛋）是工位上的加工，复用“启动加工”命令；单步预处理消耗输入、在工位或容器上生成输出，锅类多输入加工保留输入并切换锅状态，两种完成形态并存；
- 打蛋需要碗；蛋液倒进锅后碗即空出，可直接复用于装汤；
- 取得的番茄直接可切，不保留清洗步骤；
- 启动煮制后不能停止加工，但可以把锅从灶台端走，加工继续并保留进度；
- 配方按输入集合匹配，输入顺序不重要；
- NPC 按任务生成顺序排队处理冲突，不引入优先级微操；
- 当前这些基础规则均已有实现入口；正常产品流程不定义业务失败。后续产品讨论不再回到失败条件，而转向伙伴局内成长、收益/评价和更丰富顾客内容。

### 跨小关的装修、道具与 Buff

- 小关成功后从若干候选装修方向中选择一个，候选集合由关卡或剧本定义；
- “新道具 ID”指配置定义 ID（DefinitionId）：解锁一种道具种类，下一小关按标准供应实例化；不是把一个运行实例搬进下一小关；
- Buff 信息与生效状态属于当前加载的 Level；
- 当前 Level 必须保证其声明的 Buff 在该 Level 运行期间生效；
- Buff 不属于 Participant 私有数据，也不作为 Match 全局数据自动继承；进入其他 Level 时，以新加载 Level 的 Buff 配置/状态为准；
- 装修改变工位种类与数量（例如多一个砧板、灶台换成双口灶），同时改变空间布局；
- Buff 设计上不出现同一个 Buff 被重复获得，因此不存在同类覆盖、叠层或互斥；不同 Buff 之间也不设互斥；
- 解锁的新道具进入下一小关的标准初始供应，数量由关卡配置决定；
- 小关失败不写检查点，但装修、道具和 Buff 选择在当前进程内仍然有效，重试时继续带着它们；
- 候选装修全部展示、任选一个，互斥通过候选池不包含冲突组合来避免；
- 装修、道具、Buff 选择确认后即锁定，不能撤销重选；
- 装修同时涉及厨房工位、餐桌位置和 NPC 相关设施；
- 跨成功小关时，脏碗、干净碗池、NPC 进行中的询问或清洗任务全部延续；
- 小关成功检查点保存全部延续状态：装修与工位布局、解锁道具、Buff、厨房物料（食材、半成品、容器内容、加工进度）、脏碗与干净碗池、NPC 伙伴状态与进行中任务；
- 检查点必须清除本关订单、目标、关卡时间、得分结算上下文、Level 命令与快照水位；
- 加载检查点后回到最近一次成功小关结束后的准备状态，先做下一小关的装修、道具、Buff 选择，再进入运行；
- 检查点写入失败即阻止进入下一小关，停留在成功结算后的状态；
- 具体实例：新道具为烤箱（以配置定义 ID 解锁，进入下一小关标准初始供应；首个闭环内没有使用它的配方）；Buff 为煮制加速（由当前加载 Level 的 Buff 配置保证其生效）；
- 打蛋手持碗即可启动加工，不需要工位；与“切番茄需要砧板、煮制需要灶台”并存，加工是否需要在工位上执行按加工区分；
- 不设置业务失败条件；正常小关按营业与收尾规则自然完成；
- 该旧失败界面方向已被最新决定取代：正常产品流程不产生业务失败或失败界面；
- 关间没有营业任务，NPC 小伙伴站在一边，玩家可以和他们聊天；
- 烤箱是另一种加工工位，允许烘烤类加工；一个工位同一时刻只进行一个加工；
- 现有失败重开能力不进入正常产品流程；装修、道具与 Buff 在自然完成并形成稳定结算后进入后续检查点；
- 小关结束瞬间丢弃进行中的 NPC 任务，但不能出现中断痕迹，业务效果按完成收口（询问中的顾客照常生成订单，清洗中的碗照常变干净）；
- NPC 伙伴身份、名字、岗位和陪伴长期不变，能力成长只在小关内有效、每小关重新成长；
- 固定伙伴开局就有，人数固定，不随进度增减；每位伙伴有固定岗位，玩家不做岗位安排或局内指派；
- 伙伴第一项小关内成长能力确定为洗碗速度加快；后续能力仍可扩展为新的处理方式或覆盖范围；
- 关间和 NPC 聊天只是氛围和生活化互动，不影响数值；
- 固定伙伴人数暂定 1 位，最终人数之后再定；一位伙伴对一个固定岗位负责，任务按岗位认领后按生成顺序排队；
- 伙伴的小关内成长按完成的任务数量触发，完成一定数量后解锁新的处理方式或覆盖范围；
- 烤箱首个配方为“烤面包”：面包片（开局供应）放入烤箱，显式启动烘烤，消耗输入并在烤箱中生成烤面包；烤面包定位为配料/半成品，首个闭环内不直接对应订单；
- 多位玩家共享同一家厨房，各自控制一个角色；同时争抢同一物品或工位时，按 Tick、玩家 ID、命令序号的稳定排序仲裁；
- 仍未确认的产品数量项是固定伙伴最终人数（暂定 1 位）；业务失败已确定为不设置。

## 断线继续与 Host 暂停

首个局域网纵切采用 Host 可继续运行的方向：

- Client 断开不自动结束当前 Match/Level；
- Host 可以继续当前 Level；
- Host 可以单方面主动暂停当前 Level；
- 暂停请求在当前 Tick 收口后生效；
- 暂停时停止逻辑 Tick 和新命令生效，但保留当前运行状态以便恢复；
- 暂停生效时取消已经入队但尚未执行的命令；
- 已经开始执行的命令保留其当前进度，恢复后按既有状态继续；
- 暂停后的恢复由 Host 单方面控制，从下一个逻辑 Tick 继续；
- 断线、暂停和正常小关完成是三种不同状态；
- Client 断线不产生业务失败、积分、星级或失败结算；
- Client 断线时，Host 先收口当前 Tick，取消尚未执行的命令，释放占用/动作/工位；
- 断线玩家手持的物品不归还原位置，而是直接落地到合法的 WorldPosition；
- 已经原子成功提交的订单/动作结果保留；
- 允许原 Client 在同一 Level 内重新连接；
- 重连后 Participant 的位置和运行时状态回到初始化状态；
- 重连不回滚 Host 已经保留的世界状态和已提交结果；
- 当前已加载 Level 中的 Buff 信息由 Level 持有，并由该 Level 保证 Buff 在运行期间生效；
- Buff 不作为 Match 全局私有数据处理；进入其他 Level 时，以新加载 Level 声明的 Buff 配置/状态为准，不自动假设跨 Level 继承；
- 已解锁道具、装修和工位布局不属于重连 Participant 的私有恢复数据，而是跟随已经加载的权威 Level；重连不会重新加载、覆盖或回滚这些内容；
- 订单、物品、加工和其他厨房世界状态同样以 Host 当前权威 Level 为准；
- 主机迁移、跨设备恢复以及复杂断线恢复仍不在首个纵切范围内。

以下属于纵切必须保留的最小范围，但具体业务契约仍需在后续问题中确认：

- 两名玩家的身份与连接绑定；
- 同一 Level 内的基础断线重连，重连后 Participant 回到初始化位置/运行时状态；

- 两台物理电脑的真实局域网验收属于远期目标，不纳入近期施工。

- Host 主动关闭、进程崩溃或解散 Match 时，当前 Match 终止，不做主机迁移，不生成积分、星级或业务失败；
- 每条网络消息都带有最小基础信息：发送者身份、所属 Match/Level、消息顺序和具体正文；重连消息还携带重连凭证与已收到的消息位置，用于身份校验、去重、过期判断和状态补发；
- 首次网络验收采用同一台电脑上的 Host/Client 双进程和通用 Transport 的真实实现；当前唯一验证通用 LiteNetLib reliable-UDP adapter（不使用 TCP）；两台物理电脑的局域网验收列为远期目标，近期不做；
- Client 可以在 Level 暂停期间重连；重连后接收当前完整状态，但继续保持暂停，直到 Host 恢复；
- 重连采用当前完整状态快照，不重放断线期间的历史命令；
- Level 切换由 Host 统一加载下一 Level，并向 Client 广播新的完整状态；旧 Level 的命令全部失效，重连凭证继续用于找回原 Participant；该规则属于后续网络纵切，不进入首个单 Level 通用 Transport 施工；
- 首个通用 Transport 纵切不包含积分和星级，只验证当前做菜、订单提交、权威同步、暂停、断线、重连和一个 Level 内的完整闭环；积分/星级先在单机纯 C# 中完成，再另立网络化评分接入；
- 首个通用 Transport 纵切只施工一个 Level；Level 切换规则保留在后续网络纵切，不纳入第一版通用 Transport 施工；
- Cooking、Host、Client 和协议只依赖稳定的 Network.Runtime/Transport 抽象；现有 Cooking 专用 UDP Host/Client/Protocol 不进入迁移链路，直接退役并删除；LiteNetLib 只保留为通用 Transport Adapter，KCP 暂不引入。

## 已收敛的下一独立纵切：固定伙伴小关内成长

### Goal

在现有固定伙伴询问/洗碗权威状态上增加最小的小关内成长闭环，使伙伴完成任务后能够在当前小关获得可观察、可恢复的洗碗加速，同时不引入第二套 NPC 系统或网络协议扩张。

### In Scope

- 伙伴成长进度从 0 开始，只在询问或洗碗任务实际完成时增加 1；同一任务只能累计一次。
- 累计完成 3 个伙伴任务后立即解锁洗碗加速。
- 解锁后新开始的洗碗任务 required Tick 为 `max(1, ceil(BaseWashTicks / 2))`。
- 已经开始的洗碗任务保持开始时确定的 required Tick，不在执行中改速。
- 第三个任务完成后，同一固定 Tick 内后续新认领的洗碗任务可以使用已解锁速度。
- snapshot 暴露已完成任务数、解锁状态和当前洗碗 required Tick；canonical/SHA-256 覆盖这些字段。
- 前厅 checkpoint 覆盖成长任务数；解锁状态从任务数与配置阈值确定性派生，同 Level 恢复后保持一致。
- 下一 Level 与失败重开清零成长进度；成功收口完成的任务按实际完成计数，但进入下一 Level 后仍清零。
- 只修改单机纯 C# Cooking、ET host/checkpoint 与相应测试。

### Out of Scope

- LAN protocol、`CookingSessionHost`/`CookingSessionClient` 前厅投影与双端成长共识。
- Unity、坐标、寻路、动画、伙伴名字内容或 UI。
- 第二项成长能力、伙伴人数扩张、岗位切换、玩家指派或优先级微操。
- 跨 Level、跨大关或长期餐厅成长；Profile/SaveSlot 与 durable storage。
- 收益、货币、小费、评价、复杂评分和业务失败。

### Acceptance Criteria

- [ ] G1：完成 0–2 个伙伴任务时，新洗碗任务仍使用基础 `WashTicks`；第三个任务完成后解锁。
- [ ] G2：解锁后的新洗碗任务使用 `max(1, ceil(BaseWashTicks / 2))`；奇数 Tick 向上取整，最低为 1。
- [ ] G3：询问和洗碗完成各累计一次；未完成、取消、重复收口或无效任务不得重复累计。
- [ ] G4：解锁前已开始的洗碗任务 required Tick 不变；解锁后才开始的任务使用加速值。
- [ ] G5：任务数、解锁状态和当前 required Tick 在 snapshot/canonical/SHA-256 中确定可观察，差异会改变哈希。
- [ ] G6：解锁前与解锁后 checkpoint round-trip 均与不中断基线一致；投毒任务数或不一致 required Tick 被结构化拒绝且原对象零变更。
