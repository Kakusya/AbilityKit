写入与身份规则
每次 build 有独立 invocation ID；目录位于已验证的 run/result/build-invocation 根下，创建时必须不存在。
在采集目标实际执行时生成独立 capture ID。不要把根项目生成的 ID 当全图全局属性传播，也不要仅用项目 basename、TFM 或 PID 命名。
每次 capture 只写自己的临时文件，关闭并验证后提交为完成文件；禁止多个实例 append 同一文件，禁止覆盖已有完成记录。
每份记录绑定 run、result、build invocation、capture ID、规范化项目完整路径、实际 TFM/配置及可区分实例的属性身份，并记录输入条目数、路径、大小和 SHA256。
所有证据路径必须在该 owned 根内；拒绝越界、链接绕出、旧 run 文件和名字碰撞。源码输入可以位于已批准的仓库/SDK/package 闭包中，证据副本仍须在 owned 根内。
相同项目的不同实例分别保留。不同 capture 的相同输入可以在最终输入集合中去重，但不能丢掉实例记录；同一规范化路径出现冲突 hash 必须失败。重复 capture ID 不能当作合法重复忽略。

“完整”必须有独立依据
使用本次 native build 的结构化 MSBuild 事件作为实际执行实例和 CoreCompile/Csc 调用清单。采集目标可以发带 capture ID 的机器可读消息，利用事件上下文关联项目实例；消息本身不能充当“所有编译都已采集”的唯一证明。
校验必须从真实编译事件出发，确认每次需要采集的执行都有对应完成记录；再反向确认没有无归属的额外记录。同项目不同属性/重复实例不能被项目路径去重掩盖。编译任务暴露的实际文件输入要与采集闭包核对；无法解释的输入或关联歧义须停止。
增量跳过与实际执行应分开记录；不能把“没有 trace”解释成“应该是跳过了”。跳过需要本次引擎事件和已有有效产物身份支持。
原始事件证据、生成目标、每份 trace 及完整实例清单，在生成候选结果前绑定到受信 invocation context。候选 JSON 不得自行挑选较小清单、重算 hash 后绕过检查。复用构建同样要验证原始来源和新旧身份，不得退回旧的裸 compiler.txt 验证。

汇总时机与失败规则
只在 native build 终止且 exit 已确认、日志流完全落盘、相关写入完成后汇总。成功路径要求 native0、事件日志完整、实例与 trace 双向一致，再按固定规则排序、生成聚合记录、计算最终 hash、保存 producer receipt；之后才能进入 test。
缺失、截断、格式错误、额外实例、身份替换、hash 不符、文件仍被锁定或无法确认写入结束，都不能 Passed。native 非零保留原退出码；native0 但证据校验失败，gate 仍 Failed，native 仍如实为0。启动前所有权无法证实则 Blocked；未运行的测试保持 NotRun。禁止吞异常、不断重试争用、偷偷忽略文件或从旧目录补齐。
构建日志可能含路径和属性：原始日志保留本地受控证据，只发布脱敏摘要及 hash；不要公开配置内容。binlog 不嵌入导入文件内容。
