## Genuine UDP impairment instead of application reply suppression

Existing deliberate loss of one matching CommandResult occurs *after* LiteNet reliable message delivery. It tests application response/rebind/receipt semantics, not datagram loss, retransmission or fragmentation. Keep that test separately labelled and retained.

Recommend a user-space IPv4 loopback UDP relay, no kernel settings, firewall, external service, system proxy or LAN scanning. Per remote client allocate a dedicated loopback front UDP socket and a dedicated loopback upstream UDP socket. Client connects to that relay's front endpoint; relay forwards raw datagram bytes unchanged via upstream socket to actual Host listener. Host replies to upstream endpoint; relay sends bytes from the same front socket back to the captured original client endpoint. Host therefore sees one stable upstream endpoint per client, client sees one stable front endpoint. Relay never becomes a LiteNet peer, decodes business messages, fabricates ACKs or accesses simulation. Preserve handshake/ACK/ping/fragment/data bytes and length. Restrict endpoints to explicitly owned client and Host addresses; reject third-party datagrams and bind no public address.

Feasibility is a *proposed prototype*, not verified transparency: first run0delay/0loss relay control, prove actual LiteNet connect, framed full-baseline exact ACK/Ready, legal Pickup/Drop, >MTU full-baseline fragmentation, cached retry and clean disconnect. Verify both directions and multiple distinct clients. LiteNet endpoint/handshake behavior could require additional review; a failed transparent relay control must not be worked around by changing production transport, spoofing business replies, terminating reliable sessions at the relay, or claiming raw-loss tolerance from an application decorator. If transparency cannot be established, report concrete blocker and review another local raw datagram mechanism before testing numerical impairment.

For the actual relay, owned-copy incoming UDP payload immediately; bounded byte/count scheduled queue, one monotonic per-direction delivery scheduler and seeded decisions. No retaining a reused receive buffer or one Task.Delay task per unbounded packet. For each direction use separately recorded fixed seeds and an incrementing datagram index; Bernoulli loss applies to each raw datagram (including retransmissions), not each logical command. Delay=max(0,D+integer jitter uniformly[-20,+20]ms); jitter may naturally reorder packets, record actual reorder without silently enforcing original order. No extra duplication/corruption/bandwidth limiter in this matrix. Do not claim an exact1/5% realized rate: report offered datagrams, intentionally dropped, forwarded, bytes, queues/high-water and observed realized percentages per direction. Record actual scheduling delay versus target. Unexpected socket errors or relay queue overflow invalidate the *configured network experiment*; do not hide them in planned loss. Proposed relay safety cap64MiB/65536datagrams is diagnostic-resource protection only, not a larger Session/transport budget. Overflow retains a failed artifact and orderly closes only its own sockets/processes.

Use impairment from before actual connection through warmup/sample/drain so setup resilience is not excluded invisibly. A distinct recovery phase disables impairment after a scripted connection break, performs legitimate current-instance rebind/current full ACK, checks cached same-ID retry, then executes new legal work. Record transition timestamps and which counts belong to sample/recovery. Callback tasks only copy/schedule bytes; only existing Host owner calls Tick. Relay owner has no gameplay authority.
