## Production flow and actual Busy reachability

`CookingNetworkSessionHost.ProcessOwnerFrame` holds the reentrant monitor `_gate`, processes close markers/prefix, calls CaptureFullState, maps inputs into `_waiting`, and calls real adapter ConsumeFrame synchronously. Adapter captures, admits real Host envelopes, invokes Tick, drains actual dispositions, then captures again. The outer Session completes dispositions before accepting the final capture. Ordinary owner calls are serialized; a mapped admitted waiter is normally resolved in that same frame, not deliberately left pending for another external Start callback. A second thread cannot legally enter Host owner APIs to manufacture Busy. Merely queuing a wire command then triggering BeginPreparation does not prove mapped/admitted-waiter Busy.

Host `NetworkCaptureUnavailable` returns Busy while `_ticking`, `_inFlight`, preparation mutation/initialization, lifecycle publication or generation staging is active. Existing real Factory.OnCreate reentrant capture proves Busy false/null during Start and healthy after, but ordinary Session cannot Start an already-running Host again just to exercise it. Neither reflection nor a fabricated `new CaptureResult(false, Busy, null)` establishes real ET reachability.

### B1 — genuine real-port Busy with an executing waiter, explicitly trusted callback reentry

Use a new isolated actual-ET fixture with an automatic recipe whose public `ICookingProductIdAllocator` calls a single armed callback **once during real fixed-tick output allocation**, then returns a valid unique product ID. Start it through public commands; choose required ticks so allocation occurs in a later frame after baseline handshake is Ready. In that frame, send one additional legitimate framed command (for another independent item/player if necessary), so Session maps it and real adapter admits it before Tick. The fixture records actual admission via returned outer frame, not client-send count.

The allocator callback first calls the **same real adapter** CaptureFullState and records the genuine Busy/null result. It then calls the existing Session ProcessOwnerFrame on the **same owner thread**, once, while the parent Tick is active. This reaches the Session's genuine CaptureFullState Busy branch with its outer mapped waiter. No fake port, new simulation, private field mutation, parallel owner, manual replacement of frame results or artificial busy flags. Use a guard set before callback reentry so it cannot recurse indefinitely. Allocator does not mutate the domain or call Tick; it observes port Busy and invokes the Session's public owner pump as a deliberately reentrant trusted integration callback.

Important qualification: this is **not an ordinary network-callback path** (callbacks only enqueue) or a claimed naturally concurrent main-loop scenario. It is a deliberate trusted extension reentry. Host capture is explicitly designed to return Busy for such reentry; Session currently has no equivalent `_processingOwnerFrame` guard. Root must explicitly approve this integration fault-script interpretation rather than presenting it as usual network behavior. The plan proposes it because it gives real ET Busy, actual execution and actual Session waiters without a fabricated authority.

Assertions:

1. Callback recorded exactly once, same owner thread; genuine real-port Busy false/null; reentrant Session result null; no Host clock advance from the nested owner pump and no second authority factory construction. Do not call Observe/Export while Host is mid-Tick to inspect a damaged intermediate world; compare pre-parent and post-parent complete images instead.
2. While nested Busy is active no new complete baseline or Ready is emitted, previous passive complete image remains frozen but clients are marked unsynchronized/unready; every affected caller receives an explicit bounded response rather than hanging.
3. Outer real frame's actual admission/disposition and post-Tick full state remain authoritative. If a user command was already committed in the outer frame, it must not be reported as never executed or repeated. Check one domain receipt, one item transition, one automatic product identity and allocator increment, then current complete image is published and exact ACK permits recovery.
4. Cached same-stable/payload retry agrees with the real first execution receipt; a fresh legal command after exact current ACK succeeds. Compare business identity/version/receipt/tombstone invariants, not a frozen overall Recipe.Version across legal parent ticks.

Source uncertainty to report immediately if reproduced: nested MakeUnavailable currently terminalizes `_waiting` with Busy and removes those correlations before the outer frame returns its real Executed dispositions; therefore a retained network Terminal Busy could outlive an actual domain commit. This is a **source hypothesis**, not a verified defect. Do not weaken assertions to accept a cached Busy for an already-executed command, fabricate Accepted or rewrite production during test ownership. Preserve actual red and send it to root for separate contract/source review.

If root rules out owner-pump callback reentry, mark B1 outside normal legal scheduling and retain the already accepted real-port Busy proof. A minimal delegating decorator may record a genuine Busy sampled in the allocator and expose it once to Session after the real frame, but that **injects capture-publication failure timing** and is not a naturally returned final real-adapter capture. It must be labelled fault-injected composition, not ordinary live reachability. Synthesizing a Busy enum without calling real capture is a fake-Busy control and is not the preferred proposed test. No plan promises the impossible ordinary cross-frame waiter condition.

Create a **new physical peer**, send genuine Join with configured credential, and process owner frame: expect typed terminal Rejected/Disposed, no Joined, no Ready, no new baseline and no domain/allocator access. Never inspect disposed Host Observe to manufacture a before/after hash; retain the pre-dispose frozen DTO and compare that Session retains only its unsynchronized last-good display.

Close the new peer and dispose Session idempotently in correct owner order. Assert terminal response occurs within a bounded pump and new Session construction over the disposed real adapter fails with capture unavailable. Existing deferred `disposed` case already proves old exact ACK cannot leak Ready; do not duplicate all five deferred transitions. Session.Dispose itself is terminal and ProcessOwnerFrame throws ObjectDisposedException by contract, not a recoverable authority-disposed Ready path.

### Unreachable/defensive branches

- Healthy frozen cleanup Stop command rejection due disappeared worker/process cannot be forced via ordinary owner schedule: capture→cleanup creation→admit→Tick occurs in one owner critical path with no intervening domain mutation. Existing actual admission failure controls and structured cleanup handling remain, but privately deleting a process would not establish a legal gameplay failure path.
- Cross-source logical duplicate survivor in ordinary Session is prohibited by participant-qualified IDs and single active binding; valid supersession cancels the old source before new mapping. Lower real adapter partial/all cancellation is the correct proof; same-generation duplicate correlations in Q4 are legal and test different waiter behavior.
- Closed marker capacity is the shared connection slot, not a second independently injectable tombstone store. Slot held until owner close must be tested through public lifecycle, not reflection.
- Fault/Disposed/budget-unavailable are latched terminal for the existing Session; Busy is transient. Tests cannot expect Faulted→healthy or bound exhaustion→Ready in the same instance by changing a test flag.
