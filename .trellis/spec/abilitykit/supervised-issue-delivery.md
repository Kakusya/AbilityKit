# 协调审计与执行者交付

2026-10-04 owner 决定：协调者完全接替 dot，负责方案审议、Issue 组织、调度和最终验收；执行者在 Orca 受管 worktree 中实现。历史 dot 审阅继续作为来源，不再等待该角色回复。本约定配合 [Trellis workflow](../../workflow.md) 使用，先在 Issue #6 试行；文档落地不代表完整流程已验证。

## 职责与权威

- Owner 决定产品目标和授权边界。协调者在已授权范围内拆分任务、审议计划、派发、核对原始证据、组织修复与收尾；普通工程选择不重复请求批准。
- 执行者负责指定文件和验收用例，提供 commit、实际命令、结果与遗留项；不自行扩大范围、改变标准、合并、发布或删除工作树。协调者保留独立验收责任。
- Issue 正文保存当前目标、范围、优先级、依赖、验收标准及 task/PR 链接；评论保存有日期和 SHA 的决定。Trellis 是工程计划、状态、研究与证据的权威，PR 是代码差异和审阅入口。摘要互相链接，不复制完整计划或维护第二套完成状态。
- 标签表示调度状态，不能扩张授权。某个 Issue 的合并、远端写入、发布或清理授权不得自动用于其他 Issue；恢复时核对当前用户指令和最新明确决定。

## 最小交付顺序

| 阶段 | 责任与出口 |
| --- | --- |
| 领取 | 协调者读最新 Issue、依赖、AGENTS/progress 与 task；记录真实 base/dirty、已有 worker/进程及文件归属 |
| 规划 | 明确行为差异、允许文件、不变量、验证方法和原始失败；复杂任务完成 PRD/design/implement/manifests 并经协调者审议后启动，小任务使用轻量 PRD |
| 实施 | 一个有界派发指定唯一 owner；执行者只改授权范围，保留其他人的改动；大任务分可独立审阅的小段 |
| 自检与提交 | 执行者运行适用检查，保留原始结果和失败；最终运行证据绑定源码与二进制身份，不靠摘要或 exit0 宣称通过 |
| 独立审计 | 协调者审阅最终 diff、受影响消费者、证据与关键正反控制；发现阻塞问题退回修复并复审，审计结束不等于通过 |
| 集成 | 在已有合并授权下，将已审阅提交合入目标分支；检查合并后的实际源码/契约并运行必要集成检查，不能直接挪用失配产物 |
| 收尾 | 证据迁出并验证、更新路由、记录验收和 task 归档；确认无活动任务/进程且改动已合并或保存后，按授权删除 worktree并核实实际删除 |

使用 Passed / Failed / Blocked / Skipped / NotRun；纯文档检查可以按文档范围 Passed，.NET、Unity、物理 LAN 或 CI 未运行不能被连带通过。代码完成、接受、合并、Issue 关闭、task 归档和工作树删除分别记录。合并后检查失败时保留失败并修复或按已审议方案回退，不按完成收尾。

## 调度与并行

优先级回答“多重要”，依赖回答“能否开始”。先处理使证据失真或阻塞后续的基础问题，再按影响范围、解锁价值和风险排序；Issue 编号不是执行顺序。依赖写到所需能力，不以整项无关工作完成作为隐藏前置。blocked 项给出具体缺口、解除证据与下一责任人；不能通过改标签绕开设计或环境门。

优先级只设四档：P0 为正在造成损失、必须打断当前工作的故障；P1 为当前里程碑阻塞或验收证据失真；P2 为已批准的正常交付；P3 为可延期改进。协调者维护一个有序的可执行队列，先按依赖过滤，再比较优先级、解锁价值和变更风险。优先级不是实施授权，也不让缺少前置条件的事项直接开工。

默认一个实施 worker 加协调者审计。只有范围、公共契约和资源无冲突时才扩大到两个实施 worker；同一文件、schema/DTO/hash、生成物或 writer 只能有一个 owner。不同 worktree 不保证端口、进程和构建输出隔离；本仓库既有 .NET 独占验证窗口仍串行。研究或测试准备可在明确边界内并行，合并顺序和集成检查预先指定。

执行模型按任务明确指定，启动时核对实际 model/effort；Issue #6 指定 GPT-6.1-Sol / medium，不据此假定其他任务已选定模型。若连续两轮修复仍不能消除同类阻塞，协调者先重拆任务、补足因果证据和测试；需要改变用户指定模型时明确说明并取得相应授权。不能降低验收标准来匹配模型能力。

## 派发与恢复

Orca supervised orchestration 管理运行中的 Task/Dispatch；Trellis 管理工程任务。派发写明目标文件、具体变更、不变量、所有权、可观察验收和停止边界。核实输入接受与实际 turn 开始，等待合法 worker_done 后处理报告并决定复用或释放。没有输出、超时或状态文件不能证明进程已退出，不能因此重启第二个写入者。

大任务在可验证的提交处交接：记录已完成范围、失败证据、下一段允许修改的文件和未完成出口，再让相同指定模型的新会话继续。结束一个切片的 Dispatch 不代表整个 Issue 完成；缩小派发范围必须由协调者明确记录，不能让执行者自行删掉验收项。审计除复跑既有测试，还应从合同独立构造关键反例；自检全部通过不替代独立审计。

协调者的反馈必须被执行者实际读取；入队回执不等于已处理。发现提示仍在输入框时先核对原提示和当前运行状态，再恢复提交，避免重复派发。终端被用户接管或状态不可核实时保留，不能用全局 kill/reset/强删来“收尾”。每次完成后记录来源和残留资源，删除前再次核实。

## Issue 的粒度

一个 Issue 对应一个可验收结果；较大 Issue 在 Trellis 拆成有序切片，不给每次命令、每个文件或每轮审阅单独开 Issue。正文保持简短的当前合同，历史用评论和不可变提交链接追溯。范围、依赖或验收变化由协调者记录明确决定，原失败与旧证据不重写成成功。

单次即可完成、范围明确且没有跨会话追踪价值的小改动可以直接使用轻量 Trellis task 和提交记录；不强制补开 Issue。需要排队、依赖协调、跨会话恢复或独立验收的工作使用 Issue。
