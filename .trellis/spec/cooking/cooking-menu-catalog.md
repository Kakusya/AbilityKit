# Menu catalog source and mapping contract

S04 source catalog, not a level menu or a second kitchen authority. Published core Execution/YieldPortions/multiset, RequiredProcessingContainerDefinition, ContentProvenance and S05 RequiresBinding/DisposableOnSubmission map into actual formal content loading. Original v0.1 Markdown/Excel are immutable design sources.

- Source IDs plus expected names select explicit stable runtime identities. Row order cannot assign identity. Unknown/missing/duplicate IDs or ambiguous names reject; changes require explicit manifest review.
- Preserve original attachment hashes and all367 node cell/row provenance. Each node maps to shared/expanded recipes or a distinct delivery operation; count equality alone is insufficient.
- Supplies, preparations, intermediate stages and finished products have separate DefinitionIds; recipes/processes/stations/vessels/order templates have separate typed IDs. Ketchup/fresh sauce and instant/fresh tea differ; D28 has no tea.
- Inputs are positive integer portion multisets. Stage expansion must preserve original direct multiset. Independent branches remain independent; stage order is a graph of real output objects, never row ordering or a MustLast label alone.
- Actual thermal carriers persist through load/heat/unload; runtime validates required processing vessel. Serving vessels are distinct. New hot/cold cups are disposable world supply and refill dependencies; plates/bowls use existing wash pool.
- Requirements exposes production versus delivery capability closure and refill containers.31 source station discrepancies preserve missing drink-binding dependency instead of rewriting source or adding fake processing steps.
- Catalog normalization/hash includes source provenance and fixture status. Formal configuration/checkpoint identity must consume catalog/source identity before declaring actual production integration.
- Ticks1/yield2 for selected shared preps/raw8/vessels2/score100 are explicit tests, not balance.87 candidates are not a level assignment.
- Full S09-S13 acceptance requires public-command production/submission and ET checkpoint equivalence per all87 routes; static graph/catalog loads never substitute for those results.

Implementation and outstanding exact hooks: .trellis/tasks/10-02-cooking-singleplayer-menu-schema/design.md and research/core-integration-request.md. Verified commands/results stay in task check evidence, not this spec.

Preparation final recipes carry typed OutputStorageContainer from source vessel alternatives. Storage output acceptance/capacity and level dependency closure are validated separately from processing Carrier. Batch extraction must preserve units and free working vessels or use real independently supplied instances; one carrier definition is not instance-availability proof.

Shared test drivers seed only finite declared raw units and empty vessels at unique spatial anchors. They physically transfer single-yield preparation outputs to declared storage and extract batches with ServePortion; no prepared/final product is injected. ET adapters send production through TryEnqueue/Tick and restore a fresh simulation via actual checkpoint codec/host lifecycle. Driver scheduling state may survive interruption, but gameplay authority state is reconstructed from the checkpoint only. Manual handoff requires a reachable working vessel rather than one still held by another player; StopProcess must freeze elapsed progress before another player claims the same process with ContinueProcess.

All drink order templates opt into binding and serving cups opt into disposable settlement. Meals/desserts preserve ordinary delivery and washable serving containers. Bound products cannot be moved through generic take-out/processing paths; binding changes use the core BindOrder/RebindOrder/UnbindOrder operations. The initial binding increment used Recipe schema4/Level5; current format changes are recorded in the scoped-policy section below, with incompatible old records explicitly rejected. Formal content stays definition-v3 with optional backward-compatible binding/disposal defaults; menu projection opts in explicitly.

## Scoped menu Ready and runtime authorization (2026-10-03)

Reviewed productionfa2f60e17 installs one frozen trusted menu configuration into each kernel in the existing Created/Preparing configuration window. Configuration must be owner-authorized, non-closed and non-reentrant. A different second policy cannot replace it; Running/Paused/Ended cannot configure it. Ordinary gameplay admission does not expand.

Host optional ICookingMenuGameplayFactory resolves a non-null validated catalog and policy. SelectedMenuIds are the current operating subset of loaded ContentProvenance.SelectedMenus, with matching catalog SHA; loaded graph range is not a permanent permission grant. Scoped Front templates equal selected menu OrderTemplate set. Null scoped factory configuration is an error, not legacy fallback. Only absence of the optional interface keeps legacy behavior.

CompletePreparation validates the actual same owned kitchen: recipe multiset/output/process/capability/carrier/execution/completion/yield/ticks, authorized material, real source/container, qualified reachable worker and final delivery. Temporary occupancy or finite stock quantity produces warnings or ordinary recovery needs, not a new normal business failure. Structural rejection returns menu/node/relation diagnostics and leaves authoritative state unchanged.

Effective material authorization is (BaseAuthorizedMaterialDefinitions union ConfirmedMaterialUnlocks) intersect AllowedMaterialDefinitions. New supply Request/Take and new Start/PutIn/ordinary Pour/portion output respect this authorization; new recipes additionally belong to selected dependency closure. Binding enablement gates Bind/Unbind/Rebind. Already approved in-flight Receive remains available; existing processes retain progress and can finish. Pickup/Drop/TakeOut/ClearContents/DiscardItem remain recovery paths for forbidden carried state. Existing formed authorized products may move even if their producing recipe is excluded; generating new portions from that recipe is denied. Preview uses the same policy. MenuNotAuthorized is tail-appended without renumbering prior command reasons.

Level envelope8 requires explicitly present nullable MenuConfigurationIdentity and includes it in integrity; no-policy is explicit null, old envelope versions reject. Recipe5/definition3 and typed major baseline2 are separate. Restore freezes trusted scope configuration once, compares saved identity, installs actual policy before restored gameplay and Ready validation; saved data never grants permissions. Generation staging retains source immutable policy only in the private copy; a fresh successor uses its current trusted policy.

Actual proof and remaining exits stay in active task check records. This contract does not prove durable Host restart, full natural operating acceptance, narrowed carry fixtures, network or Unity completion.
